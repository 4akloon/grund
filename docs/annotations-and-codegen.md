# Annotations and code generation

Annotations are a shorter way to write the explicit API. They have no
behavior: a generator reads them with the Dart analyzer and writes ordinary
Dart on the explicit API next to your sources, which you commit. Nothing
else in your files changes.

## The annotations

They live in the packages they belong to, in libraries of their own:

| Library | Annotations |
| --- | --- |
| `package:grund/annotations.dart` | `@Module`, `@Injectable`, `@Provides`, `Bind`, `@Named`, `Scope` |
| `package:grund_http/annotations.dart` | `@Api`, `@Get`, `@Post`, `@Put`, `@Patch`, `@Delete`, `@Path`, `@Query`, `@Header`, `@Cookie`, `@Body`, `@Range`, `@Length`, `@Pattern`, `@OneOf` |

Separate libraries because the names clash: the annotation `Module` with the
base class `Module`, `Pattern` with `dart:core` and `Cookie` with `dart:io`.
The import block of a host library therefore looks like this (from
`example/lib/src/tasks/tasks_api.dart` and `tasks_module.dart`):

A library with an `@Api` class (`tasks_api.dart`):

```dart
import 'package:grund_http/annotations.dart';
import 'package:grund_http/grund_http.dart' as http;

part 'tasks_api.g.dart';
```

A library with a `@Module` class (`tasks_module.dart`):

```dart
import 'package:grund/annotations.dart';
import 'package:grund/grund.dart' as grund;

import 'tasks_module.g.dart';
```

- **`as grund` and `as http`.** The annotations are imported unprefixed; the
  explicit API is imported with a prefix, so `Module` means the annotation
  and `grund.Module` the base class you extend. The generated code refers to
  `http.HttpApi`, `http.Route`, `http.HookRef`, so an `@Api` library must
  import `grund_http.dart` as `http`; the generator reports it otherwise
  (`missing_required_import`). Unprefixed imports of the explicit API work
  where you use no annotation (a hook, a service).
- **`Pattern` and `Cookie`.** An explicit import wins over `dart:core`, so
  `@Pattern(r'^\w+$')` means the annotation in a library that imports
  `grund_http/annotations.dart`; use `import 'dart:core' as core;` if the
  library also needs the core `Pattern`. `Cookie` is ambiguous when the
  library imports `dart:io` unprefixed: write `import 'dart:io' as io;`.

## What is generated

One output per source library, next to it, with the same stem: `x.dart` gets
`x.g.dart`. What the file is follows from what the library declares:

| The library declares | `x.g.dart` is |
| --- | --- |
| `@Module` classes | a library with `mixin $Name on grund.Module` for each one. The hand-written module imports it and writes `final class Name extends grund.Module with $Name`. |
| `@Api` classes | `part of 'x.dart'` with `NameRoutes extends http.HttpApi` for each one. The host writes `part 'x.g.dart';`. |
| only `@Injectable`/`@Provides` | no file: the module that lists them generates their factories |

**A library declares one of the two.** A `@Module` and an `@Api` in one
library need the same file twice, as a library and as a part, and are a
`conflicting_outputs` diagnostic at both declarations: put modules and APIs
in separate libraries (the example does: `tasks_api.dart` and
`tasks_module.dart`). A part without its directive is `missing_part_directive`.

The generated module for `TasksModule` is its `imports`, `bindings`,
`exports` and `global` overrides; the `@Api` class becomes two bindings, the
class itself and its `TasksApiRoutes`. `example/lib/src/tasks/*.g.dart` are
the whole output for a real module and API. A generated file starts with
`// GENERATED BY grund_generator. DO NOT EDIT.` and is never edited by hand.

## What the annotations mean

- **Modules.** `@Module(imports: [...], providers: [...], exports: [...],
  global: true)`. `imports` takes `const` module instances (hand-written
  modules too, with `const` constructors); `providers` takes `@Injectable`
  and `@Api` classes and `Bind<Interface, Implementation>()`; `exports` takes
  types, `Key<T>('name')` constants and imported module types.
  `@Provides()` on a `static` method of the module is a binding of its return
  type (a `Future` result is awaited at startup), which is how runtime
  configuration enters the graph. `@Named('x')` on a class, a method or a
  parameter selects the key's name. `Scope.call` gives a `Scoped` binding.
- **Injection** uses the unnamed public constructor; every parameter is
  resolved by its type (and `@Named`), required positional and required named parameters only (an optional
  parameter is rejected).
- **Routes.** `@Api('/tasks', use: [...])` on a class, `@Get('/:id')`, `@Post`,
  `@Put`, `@Patch`, `@Delete` on its methods (`status:` and `use:` as in the
  explicit `Route`). A handler returns what the explicit one returns,
  also as a `Future`.
- **Parameters.** `@Path()`, `@Query()`, `@Header()`, `@Cookie()` read a
  `String`, `int`, `double`, `bool`, `DateTime`, `Uri` or an enum by the
  parameter's name (`name:` overrides it); a repeated `@Query()` is a
  `List<String>`. `@Body()` takes a class with `T.fromJson(Map<String,
  Object?>)`, a `List` of them, a `Map<String, Object?>` or a `Uint8List`.
  `@Range`, `@Length`, `@Pattern` and `@OneOf` constrain a parameter. A
  parameter is optional when its type is nullable or it has a Dart default;
  a present but invalid value is a 400 either way. A parameter without an
  annotation is an `HttpCtx` or a value of the call scope, resolved by its
  type (`CurrentUser user`, set by a hook).
- **Hooks.** `use: [ApiKeyHook, RolesHook(Role.editor)]`: a hook class
  (resolved from the module graph, so the API's module must provide it), a
  `const` hook instance, or a `HookRef` constant; all give the same code. See
  [http-and-hooks.md](http-and-hooks.md).

The full rules and every diagnostic code are in the READMEs of
[`grund_generator`](../packages/grund_generator/README.md) and
[`grund_http_generator`](../packages/grund_http_generator/README.md).

## Running the generator

| Driver | Command | Use it when |
| --- | --- | --- |
| `grund_cli` | `grund gen`, `grund gen --watch`, `grund dev` | the default; fast incremental analysis, hot reload |
| `grund_build` | `dart run build_runner build` / `watch` | the package already uses build_runner (see [build-runner.md](build-runner.md)) |

Both write the same bytes. Give a package one writer at a time.

The CLI writes a file only when its content changed, through a temporary
file and a rename, and writes nothing while the sources have problems. It
owns a file only if the name ends in `.g.dart` **and** the file starts with
the generator header: it never overwrites or deletes any other file (exit
code 73), and it deletes a stale header-carrying `*.g.dart` under `lib/` (the
last `@Module` of a library was removed, say). Run `grund gen` in CI and
check the tree is unchanged:

```sh
grund gen && git diff --exit-code
```

The example does the same in a test
(`example/test/generated_library_test.dart`).

## Static validation

The generator checks the module graph before it writes anything. A problem
is printed as `path:line:column: error: message [code]`, the files are left
as they were, and `gen` exits with 1:

```text
lib/src/todos.dart:30:32: error: The path /todos has no parameter :id for id; its parameters are []. [unknown_path_parameter]
```

It finds missing and circular dependencies, duplicate bindings, invalid
exports, import cycles, handler parameters it cannot bind, private types the
generated file cannot name, hook entries it cannot write, and more; the
generator READMEs list every code, and the codes are stable. What it cannot
see is checked again when the application starts, so a mistake never reaches
a request.

## Rules worth knowing

- **Deterministic output.** The same sources give byte-identical files,
  whatever the order they are read in; a change of generated output is a
  breaking change of the generator.
- **A type imported with a prefix is not resolved in an `@Api` part.** The
  part shares the imports of its host library, so a type the host imports as
  `import 'x.dart' as x;` cannot be named in the generated routes. Import
  such a type without a prefix in the library that declares the `@Api` class
  (the `as http` import is the one prefix the generator needs).
- **json_serializable and freezed write `x.g.dart` too.** One `x.g.dart` has
  one owner. `grund gen` refuses to write over a file it did not write, and
  build_runner stops with `Builders ... outputs collide` for a library both
  builders are applied to. Keep the classes those tools generate for in
  libraries without `@Module` or `@Api` (DTOs in their own files), or
  restrict `grund_build` with `generate_for` in `build.yaml`, as described in
  [build-runner.md](build-runner.md#json_serializable-and-freezed).
- Several packages: `gen` handles one package per run. A `@Module` class from
  another package (and `HttpModule` itself) is opaque to the generator: while one is imported, a dependency that no
  module of the package binds is not reported as `missing_provider` (the
  opaque module might export it). See [faq.md](faq.md#known-limitations).
