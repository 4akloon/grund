# Згенерований вивід: файл на вихідну бібліотеку

Статус: чернетка на затвердження. Змінює два місця в
`2026-10-15-grund-core-design.md`: розділ 2 (файл `lib/<package>.grund.dart`)
і розділ 6 («один файл на пакет»). Решта цього спеку лишається чинною.

## 1. Навіщо

Один `lib/<package>.grund.dart` на пакет має чотири вади, названі
користувачем: розмір і merge-конфлікти у великих пакетах; згенероване лежить
далеко від модуля; зміна одного модуля перегенеровує й перераховує весь файл
(`grund dev`, `build_runner`); фіча-пакети, виділені в окремі шари, не мають
власного виводу. Рішення: вивід розкладається по вихідних бібліотеках.

## 2. Правило виводу

- Для кожної вихідної бібліотеки `X.dart` пакета, що оголошує хоча б один
  `@Module` або `@Api`, генерується `X.grund.dart` в тому самому каталозі.
  Бібліотека без цих анотацій виводу не має (`@Injectable` без модуля нічого
  не емітить: його binding емітує модуль, який його перелічує).
- `X.grund.dart` містить міксини `mixin $M on grund.Module` для кожного
  `@Module` з `X.dart` і `HttpApi`-адаптери маршрутів для кожного `@Api` з
  `X.dart`. Адаптер `@Api` лежить у файлі свого `@Api`, а не модуля, що його
  підключає.
- Рукописний модуль імпортує свій `X.grund.dart` і пише
  `extends grund.Module with $M`. Відсутність домішки лишається діагностикою
  (`extendsModule`). `part`/`part of` не використовуються: частина ділить
  імпорти з хостом, а згенерований код потребує власного імпорту ядра з
  префіксом `grund` (збіг імен анотації й базового `Module`).
- Файла `lib/<package>.grund.dart` немає.

## 3. Посилання між файлами

- Binding модуля посилається на провайдерів, `@Provides` і `XRoutes` через
  імпорт бібліотеки, де вони оголошені (для `XRoutes` це `Y.grund.dart`).
  Циклічні імпорти `X.dart` ↔ `X.grund.dart` допустимі в Dart.
- Приватний клас чи член недосяжний з іншої бібліотеки: діагностика, як для
  інших значень, яких не можна записати в згенерованому коді.
- `ImportAllocator` — на файл; префікси `i1`, `i2`, … нумеруються в межах
  одного файла за порядком першого використання.

## 4. Перевірки й діагностики

Аналіз лишається повнопакетним: колектор будує модель усього пакета, перевірки
графа, видимості, експортів і `unsupported_use` видають ті самі діагностики з
тими самими кодами й `path:line:col`. `GrundGenerator.generate` повертає не
одну бібліотеку, а відсортований за шляхом набір «відносний шлях → вміст».
У `grund_build` білдер файла `X.dart` резолвить модулі, досяжні через імпорти,
перевіряє свої модулі проти цього графа й видає лише свої діагностики.

## 5. Запис і життєвий цикл

- Вміст детермінований (сортування, без hash-порядку), кожен файл має заголовок
  генератора, як і раніше.
- CLI пише лише змінені файли, кожен через тимчасовий файл і rename, і ніколи
  поверх файла без заголовка. Якщо джерела мають помилки, не пишеться жоден
  файл, наявні лишаються як були.
- Застарілі файли: `*.grund.dart` під `lib/` із заголовком генератора, що не
  входить у новий набір, видаляються. Файли без заголовка CLI не чіпає.
- `grund_build`: білдер `.dart` → `.grund.dart` (статичні `buildExtensions`);
  `build_runner` сам видаляє застарілий вивід. Обидва шляхи пишуть однакові
  байти й заголовок; кожен приймає файл іншого.
- `grund dev` перегенеровує й порівнює байти, тож записується лише змінене.

## 6. Тести

Golden-фікстура `users_app` стає набором файлів; тест порівнює весь набір і
перевіряє відсутність зайвих. Додаються тести: видалення застарілого файла,
«помилки джерел → нічого не записано», еквівалентність CLI і білдера по
кожному файлу, відсутність виводу для бібліотеки без `@Module`/`@Api`.
