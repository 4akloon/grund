# grund_generator

Turns the DI annotations of `package:grund/annotations.dart` (`@Module`,
`@Injectable`, `@Provides`, `Bind`, `@Named`, `Scope`) into ordinary code
on the explicit grund API and checks the module graph before the
application starts. This package is the library the drivers (a command line
tool, a build_runner builder) run; it does not read or write files itself.
It knows no HTTP: `@Api` and everything below it is the business of
`grund_http_generator`, which plugs into this package as a `Construct`;
`packages/grund_generator/test/boundary_test.dart` fails when a file of
`lib/` mentions HTTP.

```dart
import 'package:analyzer/dart/element/element.dart';
import 'package:grund_generator/grund_generator.dart';

void generate(String packageRoot, List<LibraryElement> libraries) {
  // libraries: the resolved libraries of the package's lib/.
  const generator = GrundGenerator.core();
  final package = generator.collector('shop', packageRoot).collect(libraries);
  final result = generator.generate(package);
  if (result.isSuccess) {
    // Write each entry of result.files (path -> content) under packageRoot.
  } else {
    result.diagnostics.forEach(print);
    // lib/users.dart:12:3: error: No provider for Clock in module "users"
    // (resolving: UsersService). [missing_provider]
  }
}
```

Output, one file per source library (`result.files`, path to content):

- The output of a source library `lib/users.dart` is always
  `lib/users.g.dart`, one fixed suffix (`GeneratedNames.outputPath`):
  build_runner declares its outputs per input, so the name cannot depend on
  what the library declares. What the file is follows from its content, and
  one library cannot need two kinds: units of a library and of a part for
  one path are a `conflicting_outputs` diagnostic at both declarations
  (declare modules and APIs in separate libraries). A name owned by another
  tool (`json_serializable`, `freezed`) is not guessed around: the CLI
  refuses to write over a file without the generator header, build_runner
  reports its own conflict.
- A library with `@Module` classes gets that file as a library: for each
  module `UsersModule` a `mixin $UsersModule on grund.Module` with the
  `imports`, `bindings`, `exports` and `global` overrides. The hand-written
  module imports the file and applies it:
  `final class UsersModule extends grund.Module with $UsersModule`. A
  library without a module gets no file; a library with only `@Injectable`
  or `@Provides` declarations has no output either.
- A provider a construct claims (an `@Api` class, for `grund_http_generator`)
  is written as the `emission` expression of its binding, in the place of
  the provider.
- Every file imports `package:grund/grund.dart` as `grund` and the user's
  libraries as `i1`, `i2`, ... (numbered within the file); it is formatted
  with `dart_style` for the package's language version, and starts with the
  header `// GENERATED BY grund_generator. DO NOT EDIT.`, which is how the
  tools tell a generated file from one of another tool.
- The same sources give byte-identical output, whatever the order of the
  libraries; a change of output is a breaking change of the generator. The
  bytes also depend on the `dart_style` release that resolves in your
  package: after an upgrade that changes its layout, `gen` rewrites the
  files once, with the same content.
- `PackageModel` lists modules and injectables in library-URI order, then
  source order within a library; the models of the other constructs are
  kept in `PackageModel.extensions` (`extensionModel<T>()`). This is the
  order `PackageCollector` produces, and the generated declarations follow
  it. A custom `Construct` or a hand-built model must keep that order to
  get stable output.

Diagnostics stop generation; each has a stable code (the catalog is
`DiagnosticCode`, a flat list; changing an id is a breaking change):

| Construct | Codes |
| --- | --- |
| `ModuleConstruct` | `circular_module_import`, `duplicate_binding`, `invalid_export`, `invalid_module_entry`, `invalid_module_class`, `invalid_name`, `missing_provider`, `circular_dependency`, `captive_dependency`, `not_injectable`, `invalid_constructor`, `invalid_dependency`, `invalid_provides`, `invalid_scope`, `invalid_bind`, `unsupported_constant`, `unsupported_use`, `private_declaration`, `unresolved_uri` |
| `GrundGenerator` | `duplicate_generated_name`, `conflicting_outputs`, `conflicting_provider_claim` |

The codes of `@Api` are in the `grund_http_generator` README. A syntax
error of a source file is reported by the drivers as `syntax_error`.

`unsupported_constant` is reported wherever a constant must be written into
generated code: a `@Module` entry such as an instance of a module, a key or
an annotation argument. `private_declaration` is a module that names a
private class, which the file generated into another library cannot reach;
`invalid_module_entry` is an entry of `@Module` the generator cannot read
(the message names the field and the entry). `unresolved_uri` is an
`import`, `export` or `part` of a source library that does not resolve; the
annotations it would bring cannot be read, so the library's outputs would be
dropped silently. It is reported at the directive and blocks writing and
deleting like any problem. A URI with a double extension (`x.g.dart`) is
exempt: a host library importing or including its own output has none on a
fresh checkout.

`missing_provider` and `circular_dependency` need the whole graph: when a
module is built by a function or comes from another package, the generator
cannot see its providers and skips these two checks for the whole package,
leaving them to the start of the application (`ModuleGraph.build`).

`Construct` and the model (`PackageModel`, `ModuleModel`, ...) are public,
so other packages can add constructs; the emitters (`BindingEmitter`,
`ConstantEmitter`, `TypeEmitter`, `DartString`) are public for them.

Known limitation: the file generated for an `@Api` class is a `part` of its
library and shares that library's imports, so a type the host imports with
a prefix (`import 'x.dart' as x;`) is not resolved in it. Import such a type
without a prefix in the library that declares the `@Api`.

`analyzer` is accepted from 8.1.1 to 14.x, so the generator runs on Dart
3.8 and on current SDKs.
