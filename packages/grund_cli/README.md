# grund_cli

The command line tool of grund. `gen` writes the generated files
(`X.g.dart` for `x.dart`) next to the sources from the annotations
of a package, `gen --watch` keeps it up to date while
you edit, `dev` runs the application and hot reloads it on every change, and
`init` scaffolds a new application.

```sh
dart run grund_cli gen                    # in the package directory
dart run grund_cli gen --watch            # regenerate on every change, Ctrl+C stops
dart run grund_cli gen --directory packages/shop
dart run grund_cli dev                    # run bin/main.dart, hot reload on every change
dart run grund_cli dev -t bin/server.dart -- --port 8080
dart run grund_cli init my_app            # a new package in ./my_app
dart run grund_cli init --template fullstack my_site   # pages and sessions
```

`--directory` is `-C`, `--watch` is `-w` and `--target` is `-t`. Installed as
an executable (the package declares `grund`, for example
`dart pub global activate --source path packages/grund_cli`), the same
commands are `grund gen`, `grund dev` and `grund init`. Without a
command the tool prints its usage and exits with 0.

## gen

- Reads every Dart file of `lib/` except the files the generator wrote
  (`*.g.dart` files that start with the generator's header) and runs the
  constructs of `grund_generator` (`ModuleConstruct`) and
  `grund_http_generator` (`ApiConstruct`). The result is a set of
  files, one `X.g.dart` per source library `X.dart`: a library with the
  mixins of its `@Module` classes, or a part with the routes of its `@Api`
  classes. A library that declares both is a `conflicting_outputs` problem:
  declare modules and APIs in separate libraries. A library `X.dart` that
  another tool also writes `X.g.dart` for (json_serializable, freezed) is
  not guessed around: `gen` refuses to write over that file, see below.
- Problems go to stderr, one per line, as
  `path:line:column: error: message [code]`, with the path relative to the
  package root and `/` separators on every platform; the last line counts
  them. Syntax errors have the code `syntax_error`; the generator's codes
  are listed in the `grund_generator` README. While there are problems,
  no generated file is written or deleted.
- Only syntax errors stop the analysis early. Other analyzer errors do not:
  on the first run the generated files do not exist yet, so code
  importing them does not compile. An `import`, `export` or `part` of a
  source library that does not resolve (a typo, a missing dependency) is the
  generator's `unresolved_uri` problem, so it keeps the files like any
  other; a file with a double extension (`x.g.dart`) is exempt, because
  its absence is what a fresh checkout looks like.
- Only the files whose content changed are written, each through
  `<file>.tmp` and a rename, so a running analyzer or `dev` never reads
  half a file. A file at a generated path that does not start with
  `// GENERATED BY grund_generator. DO NOT EDIT.` is never overwritten or
  deleted: `gen` fails with exit code 73 before it writes anything.
- A `*.g.dart` under `lib/` with that header that
  the new set does not contain (the last `@Module` of a library was
  removed, say) is deleted; one without the header is left alone.
- The success line says how many files were written and how long the run
  took, for example `Generated 2 files in 35 ms.` or
  `Generated files are up to date (2 files, 35 ms).`
- One package per run. A `@Module` class of another package is used from
  that package's own sources, so generate dependencies first. The
  generator cannot see into such a module (or into a module built by a
  function): it stays opaque, and `missing_provider` and
  `circular_dependency` are left to the start of the application for the
  whole package that references it.

## gen --watch

- Generates once, then after every change of a Dart file in `lib/`, with
  the analysis kept in memory: only changed files are read again.
- Events are debounced (100 ms): an editor's save or a branch switch gives
  one run. Runs never overlap; changes made during a run go into the next.
  A burst that spans the end of a run can therefore give two runs.
- Problems are printed and watching goes on; so does a failure to write the
  output (a `CliFailure`). Any other exception of a run ends the process,
  and so does an error of the file watcher's stream.
- A broken `package:grund/annotations.dart` import is an `unresolved_uri`
  problem: the run keeps the generated files and reports it.
- Files named like the generator's output (`*.g.dart`) do not start a run,
  whoever wrote them (also json_serializable's).
- The generation benchmark is not part of `dart test`:
  `cd packages/grund_cli && dart test benchmark`. On 200 files it took
  about 2.5 s cold and 0.35 s for an incremental run when this was written;
  the test fails above 10 s and 1 s.

## dev

`dev` generates like `gen --watch` and runs the application next to it:
`dart --enable-vm-service=0 --no-dds <target> <arguments>` in the package
directory, where the target is `bin/main.dart` or `--target` (`-t`, also
`--entry`) and the arguments are the ones after `--`. The VM service listens
on an ephemeral port of the loopback interface. The application's output is
passed through unchanged; `dev` adds one line per event:

```text
Started bin/main.dart (pid 4242, VM service http://127.0.0.1:40107/abc=/).
Reloaded 3 libraries in 180 ms, 2 added, 0 removed.
  + GET /hello/bye
  + GET /hello/hi
Restarting bin/main.dart: lib/src/greeter.dart changed a field, a constructor or a top-level variable.
```

- `lib/` and the directory of the target are watched; the target must be
  in a directory of the package (`bin/main.dart`, not `main.dart`).
- After every run without problems, the application is hot reloaded (the
  VM's `reloadSources`) and then reassembled (`ext.grund.reassemble`, see
  the `grund` README): singletons keep their state when their module is
  unchanged, the modules, `HttpApi`s and routes are rebuilt, the process
  and its port stay. The extension answers with what each runner added and
  removed (the HTTP server: `GET /hello/bye`), which `dev` prints after the
  summary line.
- It is hot restarted instead (the grund applications close, requests in
  flight finish, the process ends, then a new one starts) when a file
  changed a field, a constructor, a top-level or static variable or an enum
  value: a reload would keep instances without the new field. It is also
  restarted when the VM refuses the reload (for example a changed type
  parameter). The restart reason is printed.
- A reload does not run `main` again: a change of the server setup in
  `main` itself takes effect after a restart (`R`).
- While the sources have problems, nothing is reloaded: the application
  keeps running the previous code. A reload that does not compile (an error
  outside `lib/`) is printed and changes nothing either; the application is
  not restarted. A reassemble that fails keeps the previous modules and
  prints the error.
- An application that exits (or does not start) is started again after the
  next change, never in a loop.
- Changes the watcher does not see (a path dependency, `tool/`, anything
  outside `lib/` and the directory of the target) are reloaded without the
  shape check: restart with `R` after changing a field there.
- In a terminal, `r` reloads and `R` restarts (they start the application
  when it is not running). `r` also applies a change that problems held
  back, restarting when it changed a shape. Ctrl+C (or `SIGTERM` outside
  Windows) stops `dev`: it closes the grund applications and ends the
  application (`SIGTERM`, then `SIGKILL` after 2 s). In a terminal Ctrl+C
  reaches the application directly too (same process group), so it may end
  on the signal before it closed gracefully; `SIGTERM` sent to `dev` alone
  closes it first. A second interrupt while `dev` is stopping kills the
  application, restores the terminal and exits with 130. If `dev` itself is
  killed (`SIGKILL`), the application keeps running: Dart has no
  parent-death signal, so stop the orphan yourself.
- A VM service that does not answer does not hang `dev`: connecting waits
  5 s, a reload 60 s, closing the applications 5 s and the application's
  first sign of life 30 s; then the step fails with a message and `dev`
  goes on (or, for the last, stops the application until the next change).
- Open pages reload themselves. `dev` serves server-sent events on an
  ephemeral loopback port for as long as it runs and passes their URL to
  the application in `GRUND_LIVE_RELOAD_URL`; it sends `event: reload`
  after every reload whose reassemble succeeded and once a started or
  restarted application serves (the reassemble extension answers). A
  `grund_jaspr` application adds the listening script to its pages; nothing
  else changes for an application that ignores the variable.
- `dev` runs the target with `dart <target>`, not `dart run`: no implicit
  `pub get` on every restart, and one process whose `pid` is the
  application's. Run `dart pub get` after editing `pubspec.yaml`, then
  restart with `R`.

## init

`init [--template <name>] <directory>` writes a new package into a new or
empty directory; the directory name is the package name
(lowercase_with_underscores, not a Dart reserved word, and not one of the
packages the template depends on). There are two templates.

`--template api` (the default) is a JSON API written with annotations:
`pubspec.yaml`, `analysis_options.yaml`, `.gitignore`, `lib/src/hello.dart`
(a service and an `@Api` with its `part`), `lib/src/app_module.dart` (the
root `AppModule`, which imports `HttpModule` and `IoAdapterModule`) and
`bin/main.dart` (`App(root:).run(...)`, logging to the console, see
`docs/logging.md` of the repository) and `test/hello_test.dart` (a smoke
test of `GET /hello` through `TestApp` and `TestClient`, no socket; run it
with `dart test` after `dart run grund_cli gen`).
If writing fails, the files `init` created are removed again. Then:

```sh
cd my_app
dart pub get
dart run grund_cli gen
dart run bin/main.dart    # GET http://localhost:8080/hello?name=you
```

The scaffold's entry point is `bin/main.dart`, so `dart run grund_cli dev`
runs it without `--target`.

`--template fullstack` is a site written with the explicit API, served by
`grund_jaspr` with sessions from `grund_auth`: `lib/src/app_module.dart`
(`HttpModule` with the `SessionHook`, `SessionModule`, `JasprModule`, the
`AccountApi` that signs in and out through forms),
`lib/src/home_site_module.dart` (the site and its pages), the pages in
`lib/src/pages/` (`public_site.dart`, the site with its shell; a home page
that greets the signed-in user; a sign-in page), `web/styles.css`,
`bin/main.dart` and `test/app_test.dart` (the
home page and a sign-in through `TestApp`). It needs no `gen`:

```sh
cd my_site
dart pub get
dart run grund_cli dev    # http://localhost:8080
```

The session cookie is `Secure` only in product builds, so sign-in works
over plain `http` under `dev`; serve a product build behind HTTPS.

The api scaffold depends on `grund`, `grund_io` and `grund_cli` at
`^0.2.0` and on `grund_http` at `^0.3.0`; the fullstack one also on
`grund_auth` at `^0.2.0`, on `grund_jaspr` at `^0.3.0` and on `jaspr`
`>=0.23.5 <0.24.0`. To try a scaffold against a checkout of the
repository instead of pub.dev, add to its `pubspec.yaml` (with your path):

```yaml
dependency_overrides:
  grund: {path: ../grund/packages/grund}
  grund_cli: {path: ../grund/packages/grund_cli}
  grund_generator: {path: ../grund/packages/grund_generator}
  grund_http: {path: ../grund/packages/grund_http}
  grund_http_generator: {path: ../grund/packages/grund_http_generator}
  grund_io: {path: ../grund/packages/grund_io}
```

(and, for the fullstack scaffold, `grund_auth` and `grund_jaspr` the same
way).

## Exit codes

| Code | When |
| --- | --- |
| 0 | done (also when there is nothing to generate, when no command is given, and after `--watch` or `dev` stops) |
| 1 | problems in the sources: diagnostics or syntax errors |
| 64 | wrong command line (unknown command or option, `init` without exactly one directory, or with a name that is not a valid package name, a `dev` target outside a directory of the package) |
| 66 | no `pubspec.yaml` with a valid `name`, no `lib/`, or no `dev` target |
| 70 | `dev` stopped by a failure of a generation run, of starting the application or of a key action |
| 73 | a file cannot be written, a foreign file is in the way of the output, or `init` into a directory that is not empty |
| 130 | a second interrupt while `dev` was stopping |

## Own constructs

Dart cannot load constructs at run time, so a package with constructs of
its own runs the command line from `tool/grund.dart`:

```dart
import 'dart:io';

import 'package:grund_cli/grund_cli.dart';
import 'package:grund_generator/grund_generator.dart';
import 'package:grund_http_generator/grund_http_generator.dart';

Future<void> main(List<String> arguments) async {
  final generator = GrundGenerator([
    const ModuleConstruct(),
    const ApiConstruct(),
    // MyConstruct(),
  ]);
  exitCode = await GrundCli(generator: generator).run(arguments);
}
```

and calls `dart run tool/grund.dart gen`. `GenerationSession` is the
same generation as a library: `run(changed: [...])` regenerates with the
analysis kept in memory, for tools that decide themselves when to run.

## Output bytes and `dart_style`

The generated files are formatted with the `dart_style` that resolves for
your package, so their bytes follow that release. Another version (a
teammate's `pub get`, an upgrade) makes the next `gen` rewrite the files
once, with the same content; commit the result, or pin `dart_style`.

## build_runner

`grund_build` runs the same generation as a build_runner builder and
writes the bytes `gen` writes, so a package that already uses build_runner
can generate with it instead. Its README says when to use which and how the
two share a package.
